# Overboard Security & Correctness Audit — Final Report

> Generated by a multi-agent audit (8 dimension auditors + adversarial verification). 36 findings, all verified against the actual code; 0 refuted.

## Executive Summary

Overboard is a well-structured personal clipboard manager, but this audit surfaced **two critical defects that can silently corrupt or misrepresent the user's clipboard history**, plus a cluster of high-severity reliability, security, and test-integrity gaps. The single most urgent issue is that the daily/startup `maintenanceSweep()` runs a bare `VACUUM` against a database whose FTS5 external-content index is bound to VACUUM-mutable rowids — after any sweep on a database that has seen deletes (which this app does constantly), search silently returns the wrong clip's content and the FTS index can later corrupt to "database disk image is malformed."

The three things to fix first: **(1) the VACUUM/FTS rowid desync** (add an FTS `'rebuild'` or give `item` an `INTEGER PRIMARY KEY`); **(2) the CI test theater** — every UI snapshot suite is skipped on CI and the CLI/OverboardMac modules have zero tests, so regressions in the paste path and rendering ship green; **(3) the security trio** — SSRF via DNS rebinding in link previews, credential-bearing URLs bypassing secret detection, and every copied URL being auto-fetched by default. Underneath these, the actor-blocking VACUUM and the leaked-per-fetch URLSession are real runtime-health problems.

Overall health: **fundamentally sound architecture with a few sharp, shippable-today failure modes that need immediate attention.**

## Critical

### 1. `VACUUM` in `maintenanceSweep()` desyncs the FTS5 external-content index from item rowids
**`OverboardKit/Sources/OverboardCore/Store/ClipStore.swift:447`**

`item` is declared `id TEXT PRIMARY KEY` (Database.swift:83), so it has no `INTEGER PRIMARY KEY` alias and uses the implicit, VACUUM-mutable rowid. `item_fts` is a genuine FTS5 external-content table (`content='item', content_rowid='rowid'`, Database.swift:122-128), and every FTS write keys on the live `item.rowid` while search JOINs on `item_fts.rowid = item.rowid` (line 280). Per SQLite semantics, `VACUUM` renumbers rowids of any table lacking an INTEGER PRIMARY KEY, but copies the FTS5 shadow tables (`item_fts_data/_idx/_docsize`) verbatim — so after a sweep on a database with rowid gaps (e.g. 1,3,7,10 → compacted to 1,2,3,4), the FTS docids stay 1,3,7,10. `search("foo")` then matches an FTS docid and joins to a *different* clip's row (or none). Worse, the next enrichment (`attachEnrichment`/`attachLinkMetadata`) issues a contentless FTS `'delete'` keyed on the new rowid, subtracting terms from an unrelated document — escalating to "database disk image is malformed" on later MATCH queries. The gap precondition is routine: hard `DELETE FROM item` runs in `purge` (line 393) and `purgeExpiredSecrets` (line 761). Existing `MaintenanceSweepTests` use image clips with no searchText and never search after a sweep, so this is uncaught.
**Fix:** Run `INSERT INTO item_fts(item_fts) VALUES('rebuild')` immediately after VACUUM, **or** give `item` an `INTEGER PRIMARY KEY` alias so rowids are VACUUM-stable, **or** drop VACUUM. Add a regression test that performs deletes → sweep → search and asserts correct results.

### 2. Entire `OverboardMac` module has zero test coverage
**`OverboardKit/Sources/OverboardMac`**

No test target exists for OverboardMac (Tests/ has only OverboardCoreTests, OverboardCLITests, OverboardUISnapshotTests), leaving ~1140 LOC across 11 files unverified — most critically `PastebackService.swift` (UTI→pasteboard-type mapping in `buildPasteboardItems`, file-URL multi-item handling, the changeCount-guarded restore-after-paste, and marker-type tagging that prevents restore self-capture) and `ClipboardMonitor.swift` (poll-based capture/dedup and the marker-type filter that must *exactly* match PastebackService's marker so restores don't loop back into history). A regression here — e.g. `pasteboardType(for:)` dropping a UTI mapping, or `writeAndPaste`'s changeCount comparison firing on the wrong pasteboard instance — ships with CI fully green, and the blast radius is every paste/copy the user performs.
**Fix:** Add an `OverboardMacTests` target. Prioritize PastebackService's UTI mapping + marker round-trip and ClipboardMonitor's marker filter (the invariant that the two markers match is the highest-leverage thing to pin).

## High

### 3. Link-preview SSRF guard is bypassable via DNS rebinding
**`OverboardKit/Sources/OverboardCore/Links/LinkMetadataFetcher.swift:59`**

`isFetchable`/`isPrivateHost` (lines 48-95) reject only *literal* loopback/private/link-local IPs and `localhost`/`.local` names — it inspects the host string, not the resolved address. URLSession then does its own DNS resolution and connects to whatever IP the name resolves to (no pre-resolution anywhere in the fetch path). `RedirectGuard` (lines 263-277) re-validates redirect hops with the same string-only check, so it has the identical gap. With link previews on (default true), a user copying `http://attacker.example/` whose A record points at `169.254.169.254` (cloud metadata), `127.0.0.1`, or `192.168.x.x` (LAN admin endpoint) causes the app to issue a GET to that internal service — blind SSRF that can hit metadata services or trigger state-changing GET endpoints on LAN devices. The type's own comments (lines 46-47, 57) claim SSRF hardening, so this is a gap against stated intent.
**Fix:** Resolve the host and re-check every resolved address against the private-range set before connecting (or pin the connection to the vetted IP), and apply the same at each redirect hop.

### 4. `LinkMetadataFetcher` leaks a delegate-backed URLSession on every link fetch
**`OverboardKit/Sources/OverboardCore/Links/LinkMetadataFetcher.swift:34`**

On the production path, `init` builds `URLSession(configuration:, delegate: RedirectGuard(), delegateQueue: nil)`. A URLSession with a delegate keeps a *strong* reference to that delegate and to itself until `invalidateAndCancel()`/`finishTasksAndInvalidate()` is called — Apple's docs explicitly warn it "leaks memory until it exits" otherwise. There is no invalidate call anywhere in the tree, and `AppServices.fetchLinkMetadata` (line 677) constructs a brand-new `LinkMetadataFetcher()` per link. The startup backfill drains links 25-at-a-time, one per second (AppServices.swift:245-263), and post-ingest enrichment fetches one per copied link — so a few hundred links over a session leaks a few hundred URLSessions, each with its own operation queue and retained delegate, none released for the process lifetime.
**Fix:** Reuse a single long-lived session, or call `finishTasksAndInvalidate()` after `fetch` completes.

### 5. Synchronous GRDB calls (esp. `VACUUM`) hold the ClipStore actor, stalling ingest and all UI reads
**`OverboardKit/Sources/OverboardCore/Store/ClipStore.swift:445`**

ClipStore is an actor, but every DB method is *synchronous* and calls blocking `dbWriter.write/read`. A synchronous actor method holds the actor's executor for the full duration of the blocking I/O, so no other ClipStore method can run until it returns. `maintenanceSweep()` runs `PRAGMA optimize` + `VACUUM` (lines 445-448); VACUUM rewrites the whole DB and can take multiple seconds. During that window the monitor's `await store.ingest(snapshot)` is suspended (copies buffered in the AsyncStream, so delayed not lost) and any drawer/launcher summon calling `recent()`/`search()` blocks — the history UI hangs until VACUUM finishes. This also defeats DatabasePool's WAL concurrency by serializing reads behind the actor.
**Fix:** Use GRDB's async `read`/`write` (or run VACUUM off the shared writer path) so long I/O doesn't monopolize the actor. *(Related to #1 — both stem from the VACUUM in `maintenanceSweep()`; fixing the sweep's execution model addresses both, but the FTS-rebuild in #1 is still separately required.)*

### 6. Unary minus binds tighter than `^`, producing sign-wrong calculator results
**`OverboardKit/Sources/OverboardCore/Launcher/CalculatorEngine.swift:21`**

`^` is registered as a plain `.infix` symbol (line 28) and unary minus is left to the vendored Expression library, whose parser eagerly collapses a leading `-` with the next operand into a `.prefix("-")` node before `^` is applied. So `-2^2` evaluates as `(-2)^2 = 4` instead of the standard `-(2^2) = -4`. Verified against the exact symbol set via a standalone harness: `-2^2 ⇒ 4.0`, `3*-2^2 ⇒ 12.0`, `-2^2+10 ⇒ 14.0` — all sign-wrong. The launcher shows a confident calculator row with the wrong answer, no error. Every existing `power()` test uses positive bases, so this class is untested.
**Fix:** Register `^` as right-associative with correct precedence relative to unary minus, or post-correct/pre-parse the unary-minus-before-power case. Add negative-base power tests.

### 7. All UI snapshot-test suites are skipped in CI (never actually run there)
**`OverboardKit/Tests/OverboardUISnapshotTests/SnapshotSupport.swift:13`**

`Fixtures.localOnly` is `.enabled(if: ProcessInfo.processInfo.environment["CI"] == nil)`, applied via `@Suite(.localOnly)` to 6 of 7 files in the target (ActionPalette, ItemCard, LauncherActionPalette, LauncherSection, SnippetCard snapshots). CI runs `swift test` on a GitHub-hosted runner where `CI=true` is set by default — so these suites report **0 executed tests, not pass**. Any regression to card rendering, palette layout, launcher-section rendering, or secret/pinned badge state ships to main green; only a developer running `swift test` locally on a Retina Mac would catch it. Only `LauncherCommitRoutingTests` (pure routing) actually runs on CI.
**Fix:** Run snapshot tests on CI (commit reference images and pin the runner's rendering environment), or if they're genuinely local-only, make CI *report* them as skipped loudly rather than silently — and add a non-visual smoke assertion so the code paths execute.

### 8. CLI command dispatch (`Main.swift`) is completely untested
**`OverboardKit/Sources/OverboardCLI/Main.swift`** *(overlaps `Package.swift:59` — the OverboardCLITests target exists but exercises only `Output.swift`'s pure formatters)*

`OutputTests.swift` covers only `Output.swift` (ClipJSON mapping, textLine, visible). Nothing references `Overboard.run`, `ExitCode`, or `ListOptions` — the entire subcommand surface (history/search/get/copy/help), the exit-code contract scripts branch on (ok/notFound/environment/usage), `get`'s 1-based index math and its interaction with secret-filtered `recent()`, the stdin-vs-args branching in `copy` (including `isatty(0)==0` and UTF-8 decode failure), and the environment-error mapping in `runReading` (ReadOnlyOpenError vs hot-WAL DatabaseError vs generic) are all unverified. A regression returning `.ok` instead of `.notFound` for an out-of-range `get`, or breaking WAL-recovery detection, breaks downstream scripts with no test failure. The empty test target also gives *false green* confidence.
**Fix:** Add real `OverboardCLITests` cases for each subcommand, the exit-code contract, `get` index math, and `copy` stdin/arg branching.

### 9. `purge()`/`purgeExpiredSecrets()` blob-file deletion is asserted only at the row level, never on disk
**`OverboardKit/Tests/OverboardCoreTests/OverboardCoreTests.swift:191`**

The production pruning path (`purge` at ClipStore.swift:365-405, `purgeExpiredSecrets` at 744) computes a candidate blob-hash set and deletes files via `blobs.delete(hash:)` after the DB write. But `purgeTrimsHistoryAndKeepsPinned` only checks `recent()` counts and an FTS count, and `expiredSecretsArePurged` only checks `recent()` visibility. Neither seeds a blob-backed representation (>32KB) on a to-be-purged item and asserts the blob is actually gone via `blobs.exists(hash:)`, nor that a blob still referenced by a *surviving* item is **not** deleted. A regression in the `stillReferenced` set-subtraction (e.g. off-by-one in victims vs survivors) would either leak orphaned blobs forever or delete a blob a surviving representation still points at — silently corrupting a kept clip's payload — with no test failure.
**Fix:** Add tests seeding blob-backed reps on both purge-victim and survivor items, asserting on-disk presence/absence after purge.

### 10. SwiftLint version not pinned in CI
**`.github/workflows/ci.yml:21`**

SwiftLint is installed via `brew install swiftlint` with no version pin, so it can silently upgrade between runs. Because the lint job runs `--strict`, a new SwiftLint version introducing a stricter/new rule fails the entire pipeline even when no code changed — a spurious red that blocks unrelated work.
**Fix:** Pin to a specific version (e.g. a versioned formula or a lockfile/`mint`/`.swiftlint`-managed toolchain).

## Medium

### 11. Secret detection is skipped for URL clips — credential-bearing links are stored, indexed, CLI-exposed, and fetched over the network
**`OverboardKit/Sources/OverboardCore/Capture/CaptureClassifier.swift:47`**

`SecretDetector.detect` is only invoked when `kind == .text` (line 47). Any string that parses as a single http/https URL is classified `.link` (`isSingleURL`, line 92) and never runs secret detection, so `isSecret` stays false. An AWS S3 presigned URL (`...?X-Amz-Signature=...&X-Amz-Credential=...`), a magic-login/reset link with a bearer token in the query, or an OAuth `#access_token=` fragment is therefore: (1) stored with full previewText/searchText and FTS-indexed — `overboard search amazonaws` returns the live credential; (2) given a semantic embedding; (3) surfaced by CLI `history`/`search`/`get` (Output.visible filters only `isSecret`); and (4) for fetchable URLs, sent as a live HTTP GET by LinkMetadataFetcher — the credential leaves the machine. All the `isSecret`-keyed protections (provenance-nulling, search/embedding exclusion) never engage. *(The basic-auth and `#fragment` examples are stored/indexed/CLI-exposed but not network-fetched; the presigned-query path exercises every stage.)*
**Fix:** Run `SecretDetector` plus a sensitive-URL heuristic (embedded credentials, signed/presigned query params, single-use token paths) on `.link` clips too, and mask/skip-index/skip-fetch them like text secrets.

### 12. Every copied URL is auto-fetched by default — silently consuming single-use links and enabling copy-tracking
**`Overboard/AppServices.swift:637`**

`richLinkPreviews` defaults to true (AppPreferences.swift:31), so every `.link` copy triggers a live HTTP GET to that exact URL (post-ingest at 637, plus a startup backfill over all historical links at 245-263) with only a global toggle, no per-URL consent. A one-time GET-actioned URL — email-verification, magic-login, unsubscribe, password-reset — gets consumed/invalidated by the background fetch, and for any URL the remote server is notified the link was copied (tracking-pixel behavior) with the full query/fragment transmitted before the user intends to visit. Compounds #11 (link secrets aren't excluded from the fetch).
**Fix:** Default off, exclude URLs with query params / one-time-token shapes, or require an explicit user action to fetch a given link.

### 13. Multi-selection indices aren't remapped by identity when a live update reshuffles the list
**`OverboardKit/Sources/OverboardUI/Overlay/DrawerViewModel.swift:337`**

`startLiveUpdates()` re-runs `refresh(resetSelection:false, followItemID:selectedID)` on every store-change token (fires on any new capture, OCR, AI enrichment, or secret-TTL sweep while the drawer is open). In the `followItemID` branch (line 338) only `selectedIndex` is re-pointed to the anchor's new position; `multiSelection` (a `Set<Int>` of raw indices) is left untouched. If the user has multi-selected 3 items and a new item lands at index 0, the anchor follows correctly but `multiSelection`'s stale indices now point at shifted items. Running a multi-item ClipAction (⌘K) then operates on clips the user never selected. The no-`followItemID` branch only bounds-filters, so `deleteSelected()` has the same identity loss.
**Fix:** Remap `multiSelection` by item identity (id → new index) across refreshes, dropping ids that no longer exist — same treatment `selectedIndex` gets.

### 14. Launcher selection index repoints to a different row as async provider buckets splice into the middle of results
**`OverboardKit/Sources/OverboardUI/Launcher/LauncherViewModel.swift:158`**

In `scheduleSearch()`, `secondaryProviders` run concurrently via `withTaskGroup`, and each bucket is spliced into `head + buckets.flatMap(\.self) + tail` in *provider order*, not append order. `setResults()` only reclamps `selectedIndex` on overflow — never remaps by row identity. If a later-indexed provider (files/Spotlight) returns first, the user arrows down to one of its rows, then an earlier-indexed provider (snippets/clips) finishes and inserts its bucket *before* the file rows, `selectedIndex` now refers to a different row than the highlighted one. A quick ↩ commits the wrong action (paste/open/quit an unintended target). *(Trigger requires a timing inversion — an early DB provider lagging Spotlight — plus a ↩ inside the race window, so medium not high; the highlight does visibly jump.)*
**Fix:** Preserve selection by row identity across bucket splices, or freeze selection to the highlighted row's id and re-resolve its index after each `setResults()`.

### 15. Closing the ⌘K action palette doesn't restore keyboard focus to the search field
**`OverboardKit/Sources/OverboardUI/Overlay/DrawerView.swift:30`** *(same defect in `LauncherView.swift:66`)*

`ActionPalette`/`LauncherActionPalette` is inserted into the tree only while `isPaletteOpen`, and owns its own `@FocusState` that becomes first responder. On close (Esc → `closePalette()`), the palette and its focused control are removed, but neither view has an `.onChange(of: isPaletteOpen)` to set `searchFocused`/`fieldFocused` back to true — the only focus hooks are `.onAppear` (fires once) and an unrelated `previewState` change. After ⌘K then Esc, the search field has lost first-responder status, so typed characters aren't captured until the user manually clicks back into the field. The codebase already uses `onChange`-based focus restoration elsewhere (PreviewPane), so this is a missing hook, not a design choice.
**Fix:** Add `.onChange(of: viewModel.isPaletteOpen)` in both views to restore search focus when it flips to false.

### 16. `HistoryDebugView` — a self-described debug window — ships in the release menu bar with no gate
**`Overboard/OverboardApp.swift:24`**

`HistoryDebugView`'s own doc comment says it's a debug window "superseded by the drawer for daily use," yet `OverboardApp.swift` wires it into the shipping menu bar with a "History…" button and ⌘H shortcut (lines 24-28) opening a `Window(id:"history")` (63-67) — none behind `#if DEBUG`, unlike `DebugTrace.obTrace()` which *is* correctly no-op'd outside DEBUG. Every release build ships a second, unpolished, unsearchable, non-deletable/non-pinnable full-history surface reachable via a documented shortcut a user could hit accidentally alongside ⌘⇧V.
**Fix:** Gate the menu item and window behind `#if DEBUG`.

### 17. Space-free negative exponent (`2^-2`) silently fails while `2 ^ -2` works
**`OverboardKit/Sources/OverboardCore/Launcher/CalculatorEngine.swift:21`**

Verified against the vendored parser: `2^-2` throws `Undefined postfix operator ^` (caught by `try?`, returns nil) while spaced `2 ^ -2` returns 0.25 — the tokenizer resolves prefix-vs-postfix ambiguity differently based on whitespace. `2^-2` passes `looksLikeMath` gating fine, so the launcher shows **no calculator row at all** for an ordinary input (`2^-2`, `10^-3`) a user would naturally type without spaces.
**Fix:** Normalize/pre-tokenize so unspaced operator-operator sequences parse consistently, or preprocess to insert the space the parser needs. Add unspaced-negative-exponent tests.

### 18. Comma-decimal locale input never evaluates even with an operator present
**`OverboardKit/Sources/OverboardCore/Launcher/CalculatorEngine.swift:47`**

`allowedPunctuation` and `trimmedOfBareNumberCharacters` accept `,`, so `"2,5+1"` (comma-decimal, continental Europe) and `"1,000+5"` (comma-thousands) pass `looksLikeMath` and reach `Expression(...)`, which throws `Unexpected token ,` (top-level comma is an undefined infix in this symbol set) → `try?` returns nil. CalculatorEngine has zero Locale-awareness (gating/evaluate/format hard-code ASCII `.`/`,`, never consulting `Locale.current.decimalSeparator`). These are distinct from the intentional `bareNumbersAreNotMath` case (no operator) — they contain real operators and users in comma-decimal locales would expect them to compute, but they silently produce no row.
**Fix:** Make CalculatorEngine locale-aware — normalize the decimal/grouping separators per `Locale.current` before parsing (and when formatting output).

### 19. `AppMatcher` has no diacritic folding, unlike its sibling `FileNameMatcher` and the FTS index
**`OverboardKit/Sources/OverboardCore/Launcher/AppMatcher.swift:17`**

`score(query:name:)` only `.lowercased()`s both sides before prefix/initials/substring comparison — never strips diacritics. So `"cafe"` won't match an app named "Café" (`"café".contains("cafe")` is false), and the reverse fails too. This is inconsistent with the same directory: `FileNameMatcher.fold(_:)` does `.folding(options:[.caseInsensitive,.diacriticInsensitive], locale:.current)` with a passing test, and the FTS5 table uses `tokenize='unicode61 remove_diacritics 2'`. The same launcher session is diacritic-insensitive for files and clips but not apps. `AppMatcherTests` has zero diacritic coverage, so this was missed, not chosen.
**Fix:** Apply the same `.folding` as `FileNameMatcher` before comparison; add diacritic tests.

### 20. Pin/delete/clear-history actions swallow store errors with `try?`, giving no failure feedback
**`OverboardKit/Sources/OverboardUI/Overlay/DrawerViewModel.swift:406`**

`togglePinSelected()` (406), `deleteSelected()` (416), and Settings "Clear History" (`SettingsView.swift:263`) all `try? await store.<mutate>` then unconditionally `refresh()` as if it succeeded. If the GRDB write throws (SQLITE_BUSY from a concurrent VACUUM — see #5 — or disk-full/permission), the confirmation dismisses and the user gets zero indication: the item silently remains, or the user believes history was cleared when it wasn't. These are the only three UI call sites where a user-initiated *mutating* action's result is discarded entirely.
**Fix:** Propagate the error to an alert/toast, or at minimum log it, instead of a bare `try?`.

### 21. SwiftFormat version assumed but not pinned
**`.github/workflows/ci.yml:16`**

The lint job relies on SwiftFormat being pre-installed on the `macos-26` runner image without pinning a version. When the runner image updates and bundles a different SwiftFormat, formatting-rule changes fail the lint check with no code change — a spurious red tied to infrastructure drift.
**Fix:** Explicitly install a pinned SwiftFormat version in the job.

### 22. Missing documentation of Automation (AppleEvents) permission requirement
**`README.md:37`**

The README documents Accessibility (37-39) but not the Automation permission required for "Back-to-source" (Safari/Chrome tab URL capture). The feature triggers a macOS Automation prompt on first copy per browser (line 54), and `NSAppleEventsUsageDescription` is defined in code but not connected to setup docs, so users hit an unexplained prompt.
**Fix:** Add Automation to the README permissions section.

### 23. Hardcoded `MARKETING_VERSION` in Xcode project
**`Overboard.xcodeproj/project.pbxproj:303`**

`MARKETING_VERSION` is hardcoded to `0.1.0` in Debug (303) and Release (328). CI overrides it via env var during releases (release.yml:33), but local dogfood/Xcode builds report `0.1.0` regardless of commit — the About dialog lies, and dogfood bug reports cite the wrong version.
**Fix:** Derive the version from git tags at build time, or update the hardcoded value with releases.

## Low

### 24. Detected-secret payloads are persisted to disk in cleartext for the TTL window
**`OverboardKit/Sources/OverboardCore/Capture/CaptureClassifier.swift:46`**

When a text secret is detected, preview is masked and it's kept out of FTS/embeddings/CLI, but the raw payload is still written unmodified to the representation row (comment: "Secrets keep their payload (paste still works)") in an unencrypted SQLite DB. The 0700 directory (Database.swift:19) and `secretTTLMinutes` purge (default 10) bound exposure, but during that window an API token sits cleartext at `~/Library/Application Support/Overboard/overboard.sqlite`, readable by any user-level process and captured by Time Machine / backups (not constrained by 0700). Known design tradeoff (payload needed for paste).
**Fix:** Consider encrypting secret payloads at rest, or holding them in memory only until pasted.

### 25. History pruning trims by `lastUsedAt` while the UI ranks by frecency — a reused item can be purged while still visible
**`OverboardKit/Sources/OverboardCore/Store/ClipStore.swift:376`**

`purge(keepingLatest:)` selects survivors with `ORDER BY lastUsedAt DESC LIMIT keepingLatest`, but every listing path orders by `frecencyOrderSQL` (`isPinned DESC, julianday(lastUsedAt)+0.04*min(useCount,8) DESC`). A high-`useCount` unpinned item gets up to ~1.85h of displayed-ranking lift but zero lift in the purge cutoff — near the boundary it can rank inside the visible top-N yet be deleted (cascading its reps/embedding/FTS). The user sees it, then it vanishes. Low impact (bonus saturates at ~1.85h, reorders only near-neighbors) but the two orderings should match.
**Fix:** Use `frecencyOrderSQL` in the purge survivor query too.

### 26. A single wedged AppleScript permanently disables browser-provenance / Spotify snapshots for the process
**`OverboardKit/Sources/OverboardMac/BrowserProvenanceService.swift:64`**

`fetch` races `runScript` against a 500ms timeout in a task group, but `runScript` runs `NSAppleScript.executeAndReturnError` synchronously on a *serial* `scriptQueue`. Task cancellation can't interrupt a stuck synchronous Apple Event (wedged target app or hung TCC). Once that happens the serial queue is blocked indefinitely, every later `runScript` enqueues behind it, and each `fetch` loses the race and returns nil — back-to-source provenance silently stops for all future copies until relaunch. `SpotifyNowPlayingMonitor.refreshSnapshot` (lines 27, 93) has the identical structure/failure on its own queue. Ingest itself stays responsive (bounded by the timeout).
**Fix:** Use a concurrent queue, or hard-kill/replace the stuck script rather than relying on the serial queue draining.

### 27. 200ms pasteboard polling silently drops intermediate copies within a window
**`OverboardKit/Sources/OverboardMac/ClipboardMonitor.swift:66`**

`tick` compares `changeCount` and reads only the *current* pasteboard contents. Race-free (serial MainActor timer), but if two+ distinct copies occur within one 200ms interval, `changeCount` jumps by >1 and only the most recent is read — intermediate clips are never captured. Triggered by keyboard macros, scripts issuing multiple writes, or fast ⌘C bursts. An inherent polling/latency tradeoff, not a data race, but a real history gap worth noting.
**Fix:** Accept as documented tradeoff, or shorten the interval if the gap matters more than CPU. A changeCount-driven design can't recover skipped states otherwise.

### 28. No single-instance enforcement
**`Overboard/AppDelegate.swift:20`**

Neither `applicationDidFinishLaunching` nor `AppServices.init/start()` guards against another running instance. The debug-hook comment (lines 20-21) acknowledges the scenario but only namespaces the distributed-notification channel — `startCapturePipeline()` and `registerHotkeys()` aren't deduplicated. If two instances run (e.g. an old copy in Downloads plus /Applications, launched from different paths so Launch Services treats them as distinct), both register the same global hotkeys (same combo fires in both) and both run independent ClipboardMonitor + ingest loops racing on the same `contentHash` dedup against one on-disk DB.
**Fix:** Add a single-instance lock (e.g. a file lock or running-instance check) that exits or defers the second instance.

### 29. Rapid repeated ⌘⌫ can silently re-delete the same item instead of the next one
**`OverboardKit/Sources/OverboardUI/Overlay/DrawerViewModel.swift:412`**

`deleteSelected()` reads `item = items[selectedIndex]` synchronously, then does `store.delete` + `refresh()` inside a `Task`; `items` isn't mutated until that Task completes. If invoked again (OS key-repeat, or the DEBUG "delete" notification twice quickly) before the first `refresh()` runs, the second call reads the same stale `items`/`selectedIndex` and re-deletes the SAME id. Soft-delete (tombstone) so no error/corruption, but "delete two items quickly" degrades to deleting the first one twice, leaving the second in history silently.
**Fix:** Optimistically remove the item from `items` (or guard against a re-entrant delete of the same id) before the async completes.

### 30. Calculator displays "-0" for negative-zero results
**`OverboardKit/Sources/OverboardCore/Launcher/CalculatorEngine.swift:99`**

`format(_:)` treats any value equal to its rounded value (under 1e15) as integral and uses `String(format:"%.0f", value)`. `0 * -5 == -0.0`, and `-0.0 == (-0.0).rounded()`, so `evaluate("0*-5")` yields a row displaying "-0" instead of "0" (verified: `String(format:"%.0f", -0.0)` ⇒ "-0"). Cosmetic.
**Fix:** Normalize negative zero to zero before formatting (`value == 0 ? 0 : value`, or add `0.0`).

### 31. `PreviewPane` re-implements `ClipStore.filePaths(for:)` instead of calling it
**`OverboardKit/Sources/OverboardUI/Overlay/PreviewPane.swift:248`**

`load()`'s `.file` case manually re-derives the file-path list (fetch reps → find `fileURLs` UTI → decode `[String]` → map to paths), duplicating `ClipStore.filePaths(for:)` (ClipStore.swift:787-793) which the CLI's `get` already calls (Main.swift:157). The two can drift — if `filePaths` is later hardened (filter empties, new URL encoding), PreviewPane won't pick it up and file previews go stale while the CLI stays correct.
**Fix:** Call `store.filePaths(for: item.id)`.

### 32. `force_cast` disabled without full usage verification
**`.swiftlint.yml:19`**

`force_cast` is globally disabled with the justification "Highlightr attributed-string copies are known-typed," but the codebase wasn't scanned to confirm that's the only use. If a new `force_cast` is introduced for an actual type-mismatch bug, SwiftLint won't flag it.
**Fix:** Verify all `force_cast` usages are the Highlightr pattern, then prefer inline `// swiftlint:disable:next force_cast` at those specific sites over a global disable.

### 33. Screen Recording permission not documented for `demo-screenshots.sh`
**`README.md:37`**

The permissions section omits Screen Recording, but `scripts/demo-screenshots.sh` (10-13) requires it for the terminal. A developer following the guide hits an unexplained permission denial and must read script comments to understand why.
**Fix:** Note in the README Development section that demo screenshot generation needs Screen Recording permission.
